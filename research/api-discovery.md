# Elexon API discovery and benchmarks

Verified 9 September 2026 against the production developer portal and live responses.

## Official catalogue discovery

[Elexon developer portal](https://developer.data.elexon.co.uk/) links its [Insights API catalogue](https://developer.data.elexon.co.uk/api-details#api=prod-insol-insights-api). Its public `/config.json` identifies the catalogue management URL. The public export request is:

`https://management.data.elexon.co.uk/subscriptions/000/resourceGroups/000/providers/Microsoft.ApiManagement/service/prod-insol-insights-apim/apis/prod-insol-insights-api?api-version=2022-04-01-preview&export=true&format=swagger-link`

This returns a temporary signed download link; regenerate it when needed, rather than treating the expiring URL as a source permalink. Swagger declares host `data.elexon.co.uk`, base `/bmrs/api/v1`, and 318 routes. No authentication was needed for production samples.

## Chosen source

`GET https://data.elexon.co.uk/bmrs/api/v1/balancing/settlement/system-prices/{settlementDate}?format=json`

[Official operation](https://developer.data.elexon.co.uk/api-details#api=prod-insol-insights-api&operation=get-balancing-settlement-system-prices-settlementdate).

The catalogue identifies DISEBSP and says the endpoint returns prices generated by SAA, with only the latest settlement-run message for each period. This is a retrieval snapshot, not a historical vintage database or proof of finality. The required path date is `yyyy-MM-dd`; optional format is json/xml/csv. One day per request is the documented scope; no speculative range parameter or invented numeric rate limit is used. Documented error responses include 400, 429 and 500. Respect Retry-After and back off.

JSON envelope: `metadata.datasets` plus `data` array. Fields:

| Fields | Type | Meaning/unit |
|---|---|---|
| settlementDate | date string | GB settlement date |
| settlementPeriod | integer | 1-based period within settlement day |
| startTime, createdDateTime | date-time string | UTC Z in real samples; period start and source creation time |
| systemSellPrice, systemBuyPrice | number | GBP/MWh; retain both and test equality before deriving one System Price |
| netImbalanceVolume | number | MWh; retain signed value |
| bsadDefaulted | boolean | source default indicator |
| priceDerivationCode | string | original source code, not a causal label |
| reserveScarcityPrice, sellPriceAdjustment, buyPriceAdjustment, replacementPrice | number | price context, GBP/MWh |
| replacementPriceReferenceVolume | number | MWh |
| totalAcceptedOfferVolume, totalAcceptedBidVolume | number | MWh |
| totalAdjustmentSellVolume, totalAdjustmentBuyVolume | number | MWh |
| totalSystemTaggedAcceptedOfferVolume, totalSystemTaggedAcceptedBidVolume, totalSystemTaggedAdjustmentSellVolume, totalSystemTaggedAdjustmentBuyVolume | number | MWh |

Replacement and tagged-adjustment fields are genuinely nullable; do not flag optional nulls as missing core facts. The generated schema examples have inconsistent date/SP/timestamp combinations, so they are not test fixtures. Real timestamps must be checked independently against the Europe/London settlement calendar. [Elexon's price page](https://bmrs.elexon.co.uk/system-prices) identifies System Price and NIV units; canonical domain definitions belong in METHODOLOGY.md.

Live read-only probes returned HTTP 200: 2025-10-01 had 48 rows; 2025-10-26 had 50 rows (SP1 starts 2025-10-25T23:00Z, SP50 starts 2025-10-26T23:30Z); 2025-12-31 had 48 rows. Therefore recommend Q4 2025, 1 October–31 December inclusive: a manageable complete quarter of 92 days, expected 4,418 periods including autumn clock change. Boundary probes establish availability, not full-quarter completeness; pipeline controls must prove the latter. This quarter does not establish annual seasonality. Test spring DST separately.

## Investigation endpoints

`GET /balancing/settlement/stack/all/{bidOffer}/{settlementDate}/{settlementPeriod}?format=json`

bidOffer is `bid` or `offer`; date is yyyy-MM-dd; period integer. This documented latest-calculation detailed-price endpoint returns metadata ISPSTACK and rows. Fields include date/period/startTime/createdDateTime, sequenceNumber, id, acceptanceId, bidOfferPairId, cadlFlag, soFlag, storProviderFlag, repricedIndicator, reserveScarcityPrice, originalPrice, volume, dmatAdjustedVolume, arbitrageAdjustedVolume, nivAdjustedVolume, parAdjustedVolume, finalPrice, transmissionLossMultiplier, tlmAdjustedVolume, tlmAdjustedCost. Prices are GBP/MWh, volumes MWh, costs GBP and multiplier dimensionless. Some flags/adjusted volumes genuinely return null. The 2025-10-26 SP1 offer stack returned HTTP 200. Retrieve both sides only for selected exceptions, preserving creation timestamps and checking alignment with DISEBSP.

`GET /balancing/settlement/summary/{settlementDate}/{settlementPeriod}?format=json`

The official description says summary derives from ISPSTACK, DISEBSP, MID and NETBSAD and returns decimal values as strings to avoid loss of precision. Its top-level object (no data envelope) has createdDateTime, settlementDate, settlementPeriod, startTime, adjuster, priceDerivationCode, systemSellPrice, systemBuyPrice, mainPrice and marketPrice. Each nested price has cost, volume and value. Live 2025-10-26 SP1 returned price string `24.510000000000001563`, main cost `-23.536769489838084486`, main volume `-0.960292512845291004`, adjuster `0.00`. Treat float tails as representation, not economically meaningful precision. Independently reconcile rounded price from cost/volume plus applicable adjustment; a stack match is price-mechanism evidence, not the underlying cause of a market event.

## Public quality benchmarks (review only; no copied code/design)

[lptva/gb-power-dashboard](https://github.com/lptva/gb-power-dashboard) and its [methodology](https://github.com/lptva/gb-power-dashboard/blob/main/methodology.md) demonstrate a repeatable retrieval workflow, cached raw responses, field-level provenance and visible distinction between source facts and assumptions. Adopt equivalent provenance and formula documentation, small source/coverage displays and specific limitations. Its trading, proxy-cost and optional narrative scope is broader than this service-monitoring project and is not needed here. Repository assertions are architectural benchmarks, not independently audited guarantees.

[PyPSA-GB](https://github.com/andrewlyden/PyPSA-GB) provides environment definitions, configuration-driven runs, explicit input sources and separate historical versus scenario routing. Adopt pinned dependencies, explicit window configuration, reproducible commands and source/assumption separation. Its network optimization, Snakemake and scenario infrastructure are unnecessary for this quarter of settlement observations. The useful benchmark is transparent, repeatable analysis; no model outputs or market definitions are borrowed.
